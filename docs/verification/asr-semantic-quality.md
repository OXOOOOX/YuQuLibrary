# 漏词修复、语义分句与 Qwen3-ASR 同样本对比

日期：2026-11-17。实现与隔离实测已完成；本记录不表示新版服务已部署，也不表示历史文稿已重写。

后续更新：用户确认采用修复后的 0.6B 后，已于同日上线并完成真实生产链路验证；详见[上线记录](asr-semantic-release.md)。下文保留上线之前的评测过程与当时状态，历史文稿仍未重写。

## 结论

优先修复后处理是有效的：原始识别已经包含的零时长对齐词被旧代码删除，导致大量英文漏词。修复后，固定 4 条英文样本 WER 从 15.91% 降到 5.68%，没有更换模型。取消 8 秒硬切句、恢复同一次识别的原始标点，并在读取时连接跨 30 秒保存边界的未完句，解决了用户教程中“程／序”“保／证”的拆分。

同样本换用 1.7B 后，中文严格 CER 为 8.53%，英文 WER 为 4.55%。中文分数变化全部来自数字书写差异减少，以及一处专名拼写退步；没有在这批样本上观察到中文内容识别改善。因此保留 0.6B 配置，暂不依据小样本切换默认模型。1.7B 已下载、校验并实测，可以用于后续更大且经人工确认的真实播客评测。

## 固定样本与测量方法

沿用[原始基线](asr-quality-baseline.md)全部样本、参考文本和评分器，没有按效果替换样本，也没有修改数字规范化规则：

- FLEURS 固定 revision `3c5cd38623376cb92bc769d5193891b564853276` 的 12 条中文，共 131.98 秒、422 个参考字符；4 条英文，共 36.54 秒、88 个参考词。
- 同样的 12 条中文顺序拼接为 131.98 秒音频，经过 5 个实际保存核心段。
- 中文使用字符错误率 CER，英文使用词错误率 WER；NFKC、大小写、标点处理与原基线相同，不把中文数词转换为阿拉伯数字。所有百分比均为累计编辑次数除以累计参考单位。
- 诊断保留原始 ASR 文本、完整对齐词、保存结果及各阶段时间，保存在项目外，不进入服务器日志或用户资料库。
- 同一 RTX 3080 Laptop GPU、16 GiB 显存，同一 Python 环境、BF16、SDPA、单条推理、相同 ForcedAligner、30 秒核心段和前后各 5 秒上下文。自动识别语言、确定性生成，未传入参考文本、术语提示或额外上下文。
- 生产托管空闲后进入维护，所有推理串行并持有原模型锁；没有同时运行生产推理。没有改动生产模型配置、凭据或业务数据。

最终 0.6B 与 1.7B 各 17/17 调用成功。除最初诊断和分句实现验证外，又在最终分句代码上完整复测 0.6B，报告中的耗时以这次最终复测为准。

## 漏词的实际根因

旧 `select_core_words()` 将 `endMs <= startMs` 的词全部丢弃。真实强制对齐可能把短词标为同一个时间点；这不代表识别器没有识别出它。

诊断中的 0.6B 原始 ASR 文本与修复后原始文本逐条一致，包括拼接音频的 5 个窗口。旧过滤实际删掉了 2 个中文字和 10 个英文词：

| 样本 | 被旧过滤删除的内容 |
| --- | --- |
| 中文 | 年份中的“一”、自己中的“己” |
| en_us-00 | to、the、years |
| en_us-01 | in、a |
| en_us-02 | the、and、a |
| en_us-03 | The、chemical |

现在保留这些词及模型给出的真实时间点，不编造词长或均摊时间；超出媒体尾部后被裁成零长度的词仍不恢复。对齐词与 ASR 词面无法完整匹配时明确失败，不静默删词，也不使用模型补写。

最终两个模型的 16 条独立样本，从原始 ASR 到保存文稿均为 0 个规范化编辑损失；拼接样本按核心段归属选取完整对齐词后也为 0 个编辑损失。这证明本批数据未发生后处理文本损失，不证明 ASR 自身无漏词或跨窗口永远无重复。

## 质量对比

| 测试 | 原流程 0.6B | 修复后 0.6B | 修复后 1.7B |
| --- | ---: | ---: | ---: |
| 中文独立样本 CER | 40/422 = 9.48% | **39/422 = 9.24%** | 36/422 = 8.53% |
| 英文独立样本 WER | 14/88 = 15.91% | **5/88 = 5.68%** | 4/88 = 4.55% |
| 拼接中文 CER | 45/422 = 10.66% | **43/422 = 10.19%** | 43/422 = 10.19% |

原流程诊断复跑与原基线的三个质量结果完全一致。恢复 10 个英文词只减少 9 次编辑，是因为恢复后的 `years` 与该条参考 `year` 仍有一次替换差异；剩余漏词 `or` 已在 ASR 原文中缺失，不能靠分句修复。

1.7B 相对修复后 0.6B 的逐条变化：

- 中文少 3 次编辑：`二零零二` 改为 `2002` 少 4 次格式差异，`Scotturb` 改为 `Scoturb` 新增 1 次字母删除。其余中文规范化输出不变。
- 英文少 1 次编辑：`splendourous` 改为参考中的 `splendours`；另有 `world` 改为 `words`，仍不同于参考 `word`。其他残留差异没有解决。
- 拼接中文的两模型规范化全文完全相同。

因此这里的严格 CER 改善不能表述为同等幅度的语义准确率改善。样本量很小，尚未人工逐字回听复核公开参考，也未覆盖真实多人播客、噪声、方言和中英混说。

## 时间与显存

每次独立调用都会校验权重并重新加载模型。墙钟时间含加载、解码、识别、对齐和清理；纯推理单列。下载不计入耗时。

| 指标 | 修复后 0.6B | 修复后 1.7B |
| --- | ---: | ---: |
| 16 条独立调用墙钟合计 | 312.55 秒 | 427.54 秒 |
| 131.98 秒拼接音频墙钟 | **38.05 秒** | **43.76 秒** |
| 该拼接音频模型加载 | 13.00 秒 | 16.19 秒 |
| 该拼接音频 ASR 识别 | 18.82 秒 | 19.76 秒 |
| 该拼接音频时间对齐 | 2.19 秒 | 1.54 秒 |
| 该拼接音频识别＋对齐 | **21.01 秒** | **21.30 秒** |
| PyTorch 已分配显存峰值 | 3.473 GiB | 5.810 GiB |
| PyTorch 保留显存峰值 | 3.879 GiB | 6.197 GiB |

显存指标是 PyTorch 进程统计，包含识别与对齐模型，不是整张显卡总占用。1.7B 本次拼接任务墙钟约多 15%，识别加对齐接近，额外已分配显存约 2.34 GiB。这里只有单轮串行测量，没有多次随机交替运行或长时间吞吐实验；不能把冷启动差异推断成持续吞吐结论。

## 语义分句实现与真实教程

新流程 `yuqu-qwen3-episode-v3` 保留同一次识别中的标点和词面，优先在句末标点或真实停顿处分段；段内较长句在已有分句标点处拆分，不再按 8 秒硬切。跨块合并仍受长度和时间一致性检查限制，累计文本达到 2000 字符边界时保留核心段分隔，不承诺任意长句都能合为一条。英文缩写、撇号、小数和域名有相应边界处理。参考了 [stable-ts regrouping](https://github.com/jianfch/stable-ts#regrouping-words) 和 [FunASR 标点模型的未完句处理](https://github.com/modelscope/FunASR/blob/main/funasr/models/ct_transformer/model.py) 的思路，未引入额外推理模型，也不让语言模型润色或补写原文。

保存仍以 30 秒核心段为不可变检查点，沿用保存后 ACK 和旧租约拒绝提交。跨核心段的首片段携带未完句标记，服务器在读取时合并，句子归属首段页面并保持同一个文稿片段 ID；“当前位置”读取、聊天范围选择及引用使用同一投影，聊天的 S 编号仍按提问快照生成。已经冻结的问答上下文不随新块到达而改变。原 v2 任务继续按旧版本续接；新 Worker 在服务器未提供能力字段时使用 v2。旧 Worker 无法恢复已保存的 v3 任务，升级后不能将这类未完成任务交回旧 Worker。

实际使用用户已有的《Python入门课程 —— 程序的输出（Print）》音轨，解析时长 242.927 秒。音频只读复制到隔离目录，没有修改业务媒体或旧文稿。完整运行 9 个核心段，墙钟 67.58 秒。用户指出的片段现在输出为：

| 实际时间 | 分句结果 |
| --- | --- |
| 1:54.20–1:58.52 | 对，那么要一行一句的打印，就可以每行都使用一个print。 |
| 1:59.32–2:10.20 | 要注意程序是自上而下执行的，也就是说先执行第一个print，再向下一次执行，这样也可以保证打印出的诗句顺序不会乱。 |

“程序”“保证”已完整保留在句内。“一次”等原始识别用词没有被后处理改写。该教程没有人工确认的完整参考文稿，不计入 CER/WER 表格。

另起新进程从 120 秒检查点恢复，后 5 个完整块对象与全程运行逐项严格相同；接回前 4 块后，全部分句与全程运行也严格相同，跨检查点的“程序”仍连接完整。恢复调用墙钟 44.72 秒，结果见 `tutorial-resume-verification.json`。这是实际模型从检查点重启验证，不等于本轮再次验证了操作系统强杀后的托管恢复。

## Arena 与开源候选核对

2026-11-17 查询 [Open ASR Leaderboard 的中文＋英文、排除闭源模型视图](https://huggingface.co/spaces/hf-audio/open_asr_leaderboard?version=1.16.0&tab=multilingual&languages=zh,en&proprietary=false)，固定榜单 v1.16.0，版本日期 2026-11-13。排名要求两种语言均有结果，以下是该筛选条件中的名次：

| --- | --- | ---: | ---: | ---: |

| 2 | NVIDIA Nemotron-3.5-Transcribe-30B-A4B | 3.16% | 6.13% | 4.64% |

中文为 FLEURS、AISHELL-1 的 CER 均值；英文为该版本 9 个默认数据集的 WER 均值；总分再对两种语言均值取平均。这个口径不同于本机小样本加权统计，不能直接横向比较两个表格，也不证明一句话内中英混说的表现。

- [Qwen3-ASR-1.7B-hf](https://huggingface.co/Qwen/Qwen3-ASR-1.7B-hf) 是当前榜单下最值得继续评测的升级候选，且本机已经实际跑通。
- [Nemotron 模型卡](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Transcribe-30B-A4B) 对应约 34B 总参数，BF16 示例使用 H100 80GB，NVFP4 方案要求 Blackwell。本机 16 GiB 不适合作为直接替换方案；其双语均分也未超过 Qwen 1.7B。
- [MOSS 模型卡](https://huggingface.co/OpenMOSS-Team/MOSS-Transcribe-Diarize) 提供约 0.9B、中英、时间戳、说话人区分和热词能力，适合将来做功能对比；当前榜单没有支持“比 Qwen 1.7B 更准”的证据。本轮未下载或执行。
- [Fun-ASR-Nano](https://huggingface.co/FunAudioLLM/Fun-ASR-Nano-2512-hf) 未出现在本次返回榜单中，不能据此判断优劣，需另做相同音频对比。

额外核对：Speech Arena 是语音合成听感榜；Artificial Analysis 的 [ASR 方法](https://artificialanalysis.ai/methodology/speech-to-text) 主要使用英文资料，不能单独用作中英双语选型证据。榜单、公开 API 响应和模型卡路径已保存在本轮研究材料中。
